# Walkthrough: [#302] Agent-Centric Storage Architecture & Legacy Structure Cleanup

## Context & Objective
Issue [#302](https://github.com/patternsatscale/brainsOS.ai/issues/302) addressed memory persistence and directory organization in multi-agent fleet operations:
1. **Root Cause**: In `nousresearch/hermes-agent` warm container environments, `brainsos_mcp` had an unparameterized `./memories` fallback that evaluated to `/opt/data/memories` inside the container's internal volume rather than persisting to the host data drive.
2. **Cognitive Overhead**: Partitioning agent state across disparate top-level folders (`data/souls/`, `data/agent_memories/`, `data/agent_workspaces/`, `data/agent_apps/`, `data/agent_logs/`) created operational confusion, path resolution friction, and clutter.
3. **Solution**:
   - Reorganized fleet state into an agent-centric layout (`/data/agents/<agent_id>/` with `SOUL.md`, `memories/`, `workspace/`, `subagents/`, and `apps/`).
   - Moved `cindypawford` (the web application canvas for Bawtford) into Bawtford's agent directory (`agents/bawtford/apps/cindypawford/`).
   - Cleaned up obsolete legacy top-level structures in both `os/config/` (templates) and `../data/` (live data drive): removed `agent_apps`, `agent_logs`, `agent_memories`, `agent_workspaces`, and `souls`.
   - Updated `brainsos_mcp`, `brainsos_agent`, `brainsos_memory`, and `runner-hermes` to mount, resolve, and write directly to agent-centric partitions on the host data drive.
