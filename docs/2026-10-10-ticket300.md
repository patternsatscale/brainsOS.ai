# Ticket #300 Walkthrough: Makefile Lifecycle Automation (make install / destroy) & Platform Stabilization

## Summary of Changes

During `make up` and environment initialization on fresh/reloaded workstations, three container stability defects were identified and resolved across the Control Plane, Communications Plane, and Telemetry Plane:

1. **LiteLLM Control Plane Gateway (`brainsos-control-litellm`) 0-Byte CA File Crash**:
   - In `docker/compose/compose.control.yml`, `litellm` mounted `${BRAINSOS_CONTROL_PLANE_DIR}/caddy_root.crt` to `/etc/ssl/caddy/root.crt` and set `SSL_CERT_FILE=/etc/ssl/caddy/root.crt`.
   - On a fresh setup or after clearing data, `caddy_root.crt` was initialized as a 0-byte placeholder touched during bootstrap. Python 3.13 / `httpx` in LiteLLM attempted to load certificates from this empty file when fetching pricing maps from GitHub, crashing immediately with `ssl.SSLError: [X509: NO_CERTIFICATE_OR_CRL_FOUND]` on import.
   - Furthermore, overriding `SSL_CERT_FILE` with Caddy's self-signed CA wiped out the container's standard public root CAs, breaking external HTTPS calls to LLM providers.
   - *Fix*: Removed the `caddy_root.crt` volume mount and SSL environment variable overrides (`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`) from `litellm`. LiteLLM now natively uses its system CA bundle (`/etc/ssl/certs/ca-certificates.crt`), communicates cleanly with loopback/bridge HTTP endpoints (`Ollama` and `Authentik`), and successfully verifies public HTTPS certificates.
   - *Fix*: In `docker/editor/entrypoint.sh`, updated the CA export check from `[ -f "${CADDY_ROOT_CA}" ]` to `[ -s "${CADDY_ROOT_CA}" ]`, guaranteeing empty cert placeholders are never exported into coder shell environments.
   - *Fix*: In `Makefile`, updated `up:` target to automatically trigger `scripts/setup/trust-caddy-ca.sh --export-only` after `docker compose up -d`, ensuring `caddy_root.crt` is populated from Caddy's live volume.

2. **SOGo Groupware Stack (`brainsos-app-sogo`) SQL Seed Key Collision**:
   - In `docker/sogo/entrypoint.sh`, `INSERT INTO sogo_users ... VALUES (...)` seeded user accounts for both `*@brainsos.local` and `*@${MAIL_DOMAIN}` within the same query.
   - When `MAIL_DOMAIN="brainsos.local"` (default local mode), duplicate entries like `'admin@brainsos.local'` and `'admin@${MAIL_DOMAIN}'` existed in the `VALUES` clause, triggering PostgreSQL error `ERROR: ON CONFLICT DO UPDATE command cannot affect row a second time (HINT: Ensure that no rows proposed for insertion within the same command have duplicate constrained values)`.
   - Because `-v ON_ERROR_STOP=1` and `set -e` were enabled, the entrypoint exited with an error, causing Docker to restart `sogo` indefinitely.
   - *Fix*: Separated the seed query into baseline unique accounts (including `@brainsos.local` and shortnames) and conditionally executed custom `@${MAIL_DOMAIN}` insertions only when `"${MAIL_DOMAIN}" != "brainsos.local"`.

3. **Zero-Data-Loss Database Password Synchronization (`scripts/control/reload-env.sh`)**:
   - When Docker containers are deleted but persistent database storage volumes are preserved (e.g., `/Users/pats/Development/brainsOS.ai/data/comms/sogo/db` or `data/control_plane/litellm_db`), regenerating `.env` creates new passwords. PostgreSQL does not update credentials on restart of an already-initialized data directory.
   - `scripts/control/reload-env.sh` was designed to handle this via `ALTER USER ... WITH PASSWORD`, but it used outdated container regex patterns (`^brainsos-sogo-db$`, `^brainsos-(infra-)?litellm-db$`, and `^brainsos-(telemetry-|langfuse-)?db$`).
   - Consequently, `reload-env.sh` skipped password synchronization for `brainsos-app-sogo-db`, `brainsos-control-litellm-db`, and `brainsos-telemetry-langfuse-db`, causing downstream client containers (`sogo`, `langfuse-web`) to fail with `password authentication failed`.
   - *Fix*: Updated container regex patterns in `scripts/control/reload-env.sh` to match `^brainsos-(control-|infra-)?litellm-db$`, `^brainsos-(app-)?sogo-db$`, and `^brainsos-(telemetry-langfuse-|telemetry-|langfuse-)?db$`. Added fallback to `LANGFUSE_DB_PASSWORD` directly from `.env`.

4. **`reload-env.sh` Syntax Error Resolution (Dangling `else`)**:
   - In `scripts/control/reload-env.sh`, an extra `fi` token existed within the Langfuse database password synchronization block, causing bash syntax parsing to fail with `syntax error near unexpected token 'else'`.
   - *Fix*: Removed the redundant `fi` token, and validated 100% of repository scripts via `find scripts -type f -name "*.sh" -exec bash -n {} +`.

5. **Portal Live Subsystem Viewport Detection (`packages/brainsOS-portal`)**:
   - In `packages/brainsOS-portal/src/App.tsx` and `UserProfileModal.tsx`, `isLiveHost` was gated with `window.location.hostname.includes('brainsos')`.
   - When accessing the appliance via `http://localhost`, `127.0.0.1`, LAN IPs, or custom appliance domains that do not contain `"brainsos"`, `isLiveHost` evaluated to `false`.
   - Consequently, `ViewportFrame.tsx` rendered the static HTML preview string (`previewHtml`) via `srcDoc` instead of mounting the live `/editor/`, `/mail/`, and `/proxy/ui/` iframes. In the Console preview, Explorer, settings, terminal, and theme buttons were static non-functional mock markup.
   - *Fix*: Inverted the check so that live mode is enabled by default across all hosts (`localhost`, `127.0.0.1`, LAN IPs, and custom domains), with offline mockup mode strictly isolated behind `?mock=true`. Recompiled the production bundle to `packages/brainsOS-portal/dist/`.

6. **Operator IDE (`code-server`) Remote Storage, Workspace Settings & Theme Alignment**:
   - In `docker/editor/entrypoint.sh`, added `--enable-remote-storage` and configured `enable-remote-storage: true` in `config.yaml`, ensuring VS Code persists workbench settings and state on the remote server instead of ephemeral browser storage.
   - In `docker/editor/entrypoint.sh` and `scripts/setup/setup-editor.sh`, added automatic seeding of `/data/.vscode/settings.json` so that workspace-level settings (Dark Modern theme, AI model endpoints, terminal defaults, and file exclusions) are directly loaded whenever `/data` is opened.
   - In `config/editor/settings.json`, updated `"workbench.colorTheme"` from `"Default Dark Modern"` to `"Dark Modern"` to match the exact theme identifier in VS Code 1.141.0.

9. **Self-Healing PostgreSQL Database Healthchecks & Canonical Path Anchoring**:
   - **Docker Compose Path Ambiguity**: When `docker-compose.yml` uses `include: [docker/compose/compose.*.yml]`, Docker Compose v2 resolves relative volume paths relative to the included file itself. A relative path like `../data` in `.env` resolved to `os/docker/data` instead of the canonical `../data` (`/Users/pats/Development/brainsOS.ai/data`), causing empty rogue databases to spin up.
   - **PostgreSQL Interrupted Catalog State**: When `postgres:16-alpine` started in freshly created directories or after interruptions, `initdb` created system catalogs but skipped `CREATE DATABASE "$POSTGRES_DB"`. The healthcheck `pg_isready -d $POSTGRES_DB` then failed continuously with `FATAL: database "authentik" does not exist` or `FATAL: database "langfuse" does not exist`, breaking `make ssl-wildcard` and `make up`.
   - **Self-Healing Healthcheck**: Upgraded healthchecks across all PostgreSQL databases (`authentik-db`, `langfuse-db`, `litellm-db`, `sogo-db`) in `compose.apps.yml`, `compose.control.yml`, and `compose.telemetry.yml` to automatically verify database existence and run `createdb` on-the-fly:
     ```yaml
     test: [ "CMD-SHELL", "pg_isready -U $${POSTGRES_USER} || exit 1; psql -U $${POSTGRES_USER} -d postgres -tc \"SELECT 1 FROM pg_database WHERE datname = '$${POSTGRES_DB}'\" | grep -q 1 || createdb -U $${POSTGRES_USER} $${POSTGRES_DB}" ]
     ```
   - **Pre-Spin Database Engines in `reload-env.sh`**: In `scripts/control/reload-env.sh`, added Step 0 before password synchronization to ensure all database engines are started and responsive (`pg_isready`) before executing `ALTER USER ... WITH PASSWORD`. Deduplicated repetitive password synchronization blocks.
   - **SOGo Authenticated Startup Resilience**: In `docker/sogo/entrypoint.sh`, updated the database wait loop to verify both TCP reachability and authenticated query execution (`SELECT 1`) for up to 30 seconds before proceeding, preventing container exit during password sync transitions.
   - **Control Plane LiteLLM Timeout Headroom**: In `scripts/control/start-control-plane.sh`, increased the LiteLLM readiness wait loop from 45s to 90s to account for Prisma schema migrations and OpenTelemetry export registration on cold starts.
   - **Caddy SOGo Static Asset Ingress Bypass (`@mail_static`)**: In `config/caddy/Caddyfile`, added dedicated `@mail_static` routing to proxy `/SOGo.woa/WebServerResources/*` directly to `sogo:20000` without triggering Authentik forward authentication, resolving HTTP 404s on CSS/JS resources.
   - **Dynamic Telemetry Directory Resolution**: In `scripts/setup/setup-langfuse.sh`, updated `LANGFUSE_*_DATA_DIR` defaults to dynamically resolve `EFFECTIVE_TELEMETRY_DIR` from `BRAINSOS_TELEMETRY_DIR` or `BRAINSOS_DATA_DIR` canonicalized to an absolute path, preventing stray `os/data/telemetry` folders.
   - **Clean Data Volume Anchoring**: Purged rogue `os/data` and `os/docker/data` directories, migrated telemetry data to the canonical data root, and removed dummy directories (`config.json`, `config.yaml`, `model_pool.json`, `mcp.json`) in `brainsos_hermes_runner_data` volume created by previous relative path resolution.

10. **Langfuse Authentik OIDC Single Sign-On & In-Cluster Ingress Resolution**:
   - **Root Cause 1 (Double Slash 301 Redirect)**: In Langfuse's NextAuth `CustomSSOProvider`, the OpenID configuration URL is constructed as `${e.issuer}/.well-known/openid-configuration`. When `AUTH_CUSTOM_ISSUER` was defined with a trailing slash (`.../application/o/langfuse/`), the resulting URL contained a double slash (`//.well-known/...`). Authentik and Caddy issued a `301 Moved Permanently` redirect to normalize the path. However, `openid-client`'s discovery handler strictly requires `200 OK` and aborts on redirects (`OPError: expected 200 OK, got: 301 Moved Permanently`), triggering NextAuth's `OAuthSignin` error screen.
   - *Fix*: Stripped the trailing slash from `AUTH_CUSTOM_ISSUER` across `docker/compose/compose.telemetry.yml`, `docker/langfuse/docker-compose.yml`, `docker/langfuse/.env`, and `scripts/setup/setup-langfuse.sh`.
   - **Root Cause 2 (Docker Desktop Hairpin NAT & 3500ms Timeout)**: `langfuse-web` previously attempted to discover Authentik via `host.docker.internal` / `host-gateway`. On Apple Silicon / macOS Docker Desktop, hairpinning back through the host virtual interface introduced latency spikes exceeding `openid-client`'s 3500ms timeout (`RPError: outgoing request timed out after 3500ms`).
   - *Fix*: Attached `langfuse-web` to `brainsos-ingress-net` and aliased `${BRAINSOS_DOMAIN:-local.brainsos.ai}` to `caddy` on `brainsos-ingress-net`. `langfuse-web` now resolves the appliance domain directly to Caddy over the Docker bridge in ~750ms.
   - Removed residual container (`hardcore_hopper`) to preserve host memory.

11. **Operator IDE Virtual Key Synchronization & Custom Key Alias (`${BRAINSOS_DOMAIN}/editor/`)**:
   - **Root Cause (Unique Key Alias Collision in LiteLLM)**: LiteLLM strictly enforces unique key aliases (`Key with alias '...' already exists`). When an environment was torn down via `make destroy` (which preserves runtime database volumes by default) and reinstalled via `make install`, `.env` generated a new `OPERATOR_LITELLM_KEY`. When `start-control-plane.sh` attempted to register the new key token with the preexisting alias (`brainsos-operator`), LiteLLM rejected the request with HTTP 400. Consequently, `code-server` was configured with a key that did not exist in `LiteLLM_VerificationTokenTable`, causing model discovery requests to fail with `HTTP 401 Unauthorized (token_not_found_in_db)`.
   - **Fix (Unique Key Alias Upsert & Purge)**: In `scripts/control/start-control-plane.sh` and `scripts/setup/setup-editor.sh`, updated `provision_vkey` to verify active token status, and automatically purge obsolete keys under matching aliases (`${OPERATOR_KEY_ALIAS}` and legacy `brainsos-operator`) via LiteLLM's `/key/delete` endpoint before generating the new token.
   - **Dynamic Domain Key Naming**: Set the key alias to `${BRAINSOS_DOMAIN}/editor/` (e.g. `osx.local.brainsos.ai/editor/`) and updated `docker/editor/entrypoint.sh` to configure `chatLanguageModels.json` with `LiteLLM (${BRAINSOS_DOMAIN}/editor/)`. Traffic originating from the IDE coder is now explicitly identified in LiteLLM request logs, telemetry traces, and spend dashboards.
   - **Lifecycle Integration**: Added automatic IDE container restart in `scripts/control/reload-env.sh` following control plane initialization, and added automated model catalog verification (`/v1/models` HTTP 200) to `scripts/verify/verify-editor.sh`.
