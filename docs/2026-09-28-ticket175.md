## 1. Executive Summary & Architectural Shift

Historically, custom bridge logic and tool wrappers for brainsOS capabilities resided directly inside `docker/hermes/plugins/`. This legacy design suffered from critical architectural liabilities:
1. **System Prompt Bloat & KV Cache Exhaustion**: Injecting native tool definitions directly into Hermes's tool catalog polluted system prompts with thousands of tokens of static JSON schemas, consuming precious KV cache VRAM on unified memory architectures (NVIDIA GB10 and Apple Silicon) and increasing tool hallucination rates.
2. **Tight Coupling**: Capabilities were locked inside the Hermes Agent plugin runtime rather than exposed as universal, standard protocols accessible by external clients (Claude Code, Cursor, OpenHands, standalone workers).
3. **Bypassed Testing**: Container plugins bypassed the standardized repository CI matrix (`pytest packages/*/tests`).

**Ticket #175 resolves this technical debt** by introducing `packages/brainsOS-mcp`, a standalone Model Context Protocol server built on FastMCP. It dynamically discovers and exposes capabilities across all domain packages under `packages/` (`brainsOS-memory`, `brainsOS-queue`, `brainsOS-mail`, `brainsOS-telemetry`) over standard `stdio` JSON-RPC. Hermes now interfaces with brainsOS strictly as an external MCP client (`mcp_servers` / `mcp.json`), achieving **Zero Native Tool Injection** into Hermes's system prompt and keeping the total schema footprint under a strict budget of **< 800 tokens (709 tokens achieved across 8 core tools)**. Furthermore, `docker/hermes/plugins/` has been **completely purged** from the repository.
