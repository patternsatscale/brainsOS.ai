## 2. Acceptance Criteria & Architecture Alignment

### A. Telemetry Infrastructure & Ingress Health
- **Langfuse Stack**: Configured modern Langfuse v4.38.0 with decoupled transactional Postgres, ClickHouse OLAP analytics, Redis queue, MinIO S3 object storage, and background asynchronous worker.
- **Port Mapping**: Web interface on `:3001`, ClickHouse on `:8123/:9000`, Redis on `:6379`, MinIO on `:9090/:9091`, PostgreSQL on `:5433` (preventing conflict with LiteLLM DB on `:5432`).
- **Control Plane Gateway**: LiteLLM initialized with `langfuse` and `otel` callbacks.

### B. Agent Plane & Fleet Integration
- **Agent Attribution**: `sync-agents.sh` injects `OTEL_SERVICE_NAME=hermes-<agent_id>` and `OTEL_RESOURCE_ATTRIBUTES=service.name=hermes-<agent_id>,agent.id=<agent_id>` for fleet isolation.
- **Multi-Tenant Partitioning (Rule 9)**: Telemetry streams between agents remain strictly compartmentalized by service name and user metadata.

### C. Inviolable Security Invariants
- **Rule 1 (Memory Plane Purity)**: Trace logs and caches are strictly routed to ClickHouse/Redis/MinIO volumes; `/memories` remains pure markdown.
- **Rule 2 (Inference Boundary)**: Completions route through LiteLLM gateway (`127.0.0.1:4000`), never directly to raw inference engine.
- **Rule 3 (Hardware Serialization)**: `max_parallel_requests: 1` preserved across all models.
- **Rule 6 (Control Plane Database Isolation)**: `titan-langfuse-db` runs on `langfuse-net` on port 5433, completely isolated from `titan-litellm-db` on port 5432 and `titan-litellm-net`.
