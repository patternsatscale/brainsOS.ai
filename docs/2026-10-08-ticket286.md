# Ticket #286 Walkthrough: Isolate Hermes Runner Runtime State to Named Volume & Purge Spilled Artifacts

## Summary of Changes

This ticket resolves the issue where running the Hermes agent runner container (`runner-hermes`) spilled 787 ephemeral runtime files (downloaded lazy packages, bundled skills, session history, SQLite databases, and lockfiles) onto the host filesystem within the Git-tracked private fleet repository (`${BRAINSOS_DATA_DIR}/runners/hermes`).

### 1. `docker/compose/compose.agents.yml` & `docker-compose.yml`
- Replaced the direct host bind-mount of `${BRAINSOS_DATA_DIR}/runners/hermes` to `/opt/data` with a dedicated persistent named volume: `hermes_runner_data` (`brainsos_hermes_runner_data`).
- Mounted static runner configuration files individually from the host into `/opt/data`:
  - `${BRAINSOS_RUNNERS_DIR}/hermes/config.yaml:/opt/data/config.yaml:rw`
  - `${BRAINSOS_RUNNERS_DIR}/hermes/config.json:/opt/data/config.json:ro`
  - `${BRAINSOS_RUNNERS_DIR}/hermes/model_pool.json:/opt/data/model_pool.json:ro`
  - `${BRAINSOS_RUNNERS_DIR}/hermes/mcp.json:/opt/data/mcp.json:ro`
- Declared `hermes_runner_data` under `volumes:` in both `compose.agents.yml` and `docker-compose.yml`.

### 2. `config/templates/data-repo.gitignore` & `${BRAINSOS_DATA_DIR}/.gitignore`
- Added comprehensive ignore rules for Hermes runner runtime artifacts:
  - Dynamic packages: `runners/hermes/lazy-packages/`
  - Dynamic tool skills: `runners/hermes/skills/`
  - Caches: `cache/`, `audio_cache/`, `image_cache/`
  - Logs, sessions, state, cron, kanban: `logs/`, `sessions/`, `state/`, `cron/`, `kanban/`, `sandboxes/`, `platforms/`
  - Transients & locks: `*.lock`, `.*.lock`, `*.pid`, `*.sock`, `*.log`, `*.bak*`, `.env*`, `install_id*`, `gateway_state.json`, etc.

### 3. Cleaned Local Fleet State (`${BRAINSOS_DATA_DIR}`)
- Purged all untracked spilled runtime artifacts from the host's `runners/hermes/` directory.
- `git status` in `${BRAINSOS_DATA_DIR}` dropped from **802 pending changes down to 15** (strictly intentional memory files and config edits).

### 4. Additions Outside the Original Acceptance Criteria
These landed on this branch during debugging. They are kept because they are correct and low-risk, but they are **not** part of the storage-isolation deliverable:
- **Queue worker singleton** (`packages/brainsOS-agent/brainsos_agent/worker.py`, `scripts/control/start-control-plane.sh`): `fcntl.flock` lockfile plus a pre-flight sweep of stale or duplicate `brainsos_agent.worker` processes.
- **Hermes internal memory and nudges disabled** (`config/default_runners/hermes/config.yaml`): `memory.memory_enabled: false`, `skills.creation_nudge_interval: 0`. Rationale: OKF is the single long-term memory source, and nudges spawn background LLM calls that compete for the GPU slot. (Hermes' internal memory lives in `/opt/data`, not `/memories`, so this is not a Rule 1 fix.)
- **Hermes OTLP log export disabled** (`monitoring.gateway_health_export.logs_export_interval_seconds: 5 → 0`).

### 5. Reverted on This Branch
- An earlier revision raised LiteLLM `max_parallel_requests` from 1 to 2 and added `num_retries: 3`. **Both are reverted.** Raising the slot count hid the real defect instead of fixing it (see Known Issues), and it contradicts the concurrency = 1 design (Rule 3).

## Known Issues (Out of Scope, Moved to a Follow-Up Ticket)

Live testing after this work turned up a defect in the email → Hermes dispatch path. It is unrelated to storage isolation:

- **Blocking dispatch orphans runs.** `HermesMailAdapter` holds one synchronous `POST /v1/chat/completions` open for the whole agent loop (180s timeout). On longer turns the worker times out and retries, but Hermes does not cancel the first loop. Orphaned loops plus the next queued email end up calling LiteLLM at the same time, which returns **HTTP 429** (`max_parallel_requests` saturated).
- **Errors delivered as replies.** `/v1/chat/completions` returns retry-exhaustion text as `200 OK` content, so the adapter emails it and writes it into OKF thread memory.
- **No agent-layer concurrency cap.** Hermes `gateway.api_server.max_concurrent_runs` defaults to 10.
- **Spool replay.** Dead-lettered spool files never get a `.done` marker, so they are re-enqueued on every worker restart.
- **Langfuse gaps.** LiteLLM generation traces have no `session_id`, failed turns are not reliably traced, and Hermes traces carry no agent or sender identity.

Planned fix: switch dispatch to Hermes' async `/v1/runs` API (submit → poll → one reply email with the result, or a failure email with recommendations), with concurrency = 1 enforced at both Hermes and LiteLLM.
