Project Titan · Reference Architecture · Pattern Review

The silly agent
that publishes itself

CindyPawfordBot is a haute-couture beagle who runs a website. She wakes at 02:00, reads what her fans voted for, writes HTML, and pushes it to production — unattended, six days a week. On Sunday she seals the week into a museum and swaps her own brain for a different model.

The dog is the joke. The delivery mechanism is the payload: an autonomous software publisher that never holds a credential, cannot reach its own CI config, cannot merge its own protections, and can be stopped with one command. This is the reference architecture for that pattern, and an honest review of where it holds and where it doesn't.

01 — OverviewWhat the pattern actually is

Strip the beagle away and you are left with a general problem: how do you let a language model ship code to production on a schedule, with nobody watching, without handing it the keys?

Most answers to that question either keep a human in the loop (which defeats the point) or hand the agent a token and hope (which defeats the security). Cindy's answer is a third thing: make the agent structurally incapable of the actions you're afraid of, then let it run free inside what's left. She has no credential to leak, no CI file to rewrite, no path to merge her own guard, and no second repo to wander into. What she does have is a blank canvas, a text editor, and a deadline.

The five moves

Move 01 · Custody
The agent never holds the token

Git and gh traffic is rewritten at the system level to an internal reverse proxy. Caddy attaches the GitHub credential in transit. docker exec … env | grep -i token returns nothing — and a test asserts it. (The container does still carry its own LiteLLM virtual key, a dashboard password and a Telegram token; what it never holds is a git or database credential.)

Move 02 · Blast radius
The canvas is the only writable surface

HERMES_WRITE_SAFE_ROOT is exactly three paths: /opt/data, /workspace, /app/html. Her memory plane is deliberately not among them. The published site's .github/ is bind-mounted read-only at the kernel, so a write there fails before policy is ever consulted.

Move 03 · Separation of powers
She can propose; she cannot ratify

A branch ruleset on main blocks direct pushes. A guard workflow fails any PR touching .github/**. CODEOWNERS puts those paths under a human. The agent that writes the code is not the agent that admits it.

Move 04 · Reversibility
Every era is a git tag

Weekly seal-and-reset snapshots the canvas, cuts archive/cindy-<slug>, appends to a ledger, then wipes and reseeds. Rollback is a checkout. Disaster recovery replays the tags. Nothing published is unrecoverable.

Move 05 · Kill switch first
Pause the container, then revoke the key

emergency-stop.sh halts the container before it tries to delete the LiteLLM virtual key — the guaranteed control runs first, the best-effort one second. Correct ordering, which is rarer than it should be.

Move 06 · Declarative truth
One manifest generates the fleet

config/agents.yaml is the single source of truth. Compose files, Caddy routes, per-agent runtime config, cron jobs and virtual keys are all generated from it. CI drift-gates the two that matter most — the compose file and the Caddy routes — so you cannot hand-edit your way out of the container or ingress model. Cron and key provisioning are generated but not drift-checked.

The honest framing

The credential-custody and tenant-partition halves of this design are genuinely strong and regression-tested. The containment half — egress filtering, capability dropping, resource ceilings, an audit log — is thinner than the prose around it. Section 07 says exactly where. Present the token-injection pattern as secret custody, not as egress control, and the architecture describes itself accurately.

03 — The Daily LoopCindy's logic, step by step

The entire behavioural specification is two cron entries in config/agents.yaml and a 58-line persona. There is no orchestration code, no task graph, no retry ladder. That minimalism is deliberate — and it's the part of the design most worth arguing about.

# config/agents.yaml — the whole schedule
cron:
  - id: "daily-feature-drop"
    schedule: "0 2 * * 1-6"        # 02:00, Mon–Sat
    prompt: "Using your active coding engine (cindy-active-coding-model),
             inspect the live site files in /app/html, review top community
             ideas, and implement 1-2 spontaneous haute-couture canine features."
  - id: "weekly-era-reset"
    schedule: "0 2 * * 0"          # 02:00, Sunday
    prompt: "Write closing recap.json, touch .archive-ready to trigger the
             archive seal, wait for clean slate reset, and brainstorm next week."
Trust assumption worth stating

Several load-bearing behaviours — cron dispatch of jobs.json, enforcement of HERMES_WRITE_SAFE_ROOT, the Telegram allowlist, session freshness, and the OTLP export interval — are implemented inside the upstream nousresearch/hermes-agent image, not in this repo. The configuration is correct and present; the enforcement is vendored. Anyone adopting this pattern should treat the runtime as a dependency to be verified independently, not as part of the reviewed surface.

Monday through Saturday — the feature drop

TRIGGER · scheduler
02:00 — the job fires

The manifest's cron block is compiled by sync-agents.sh into data/workspace/cindy-pawford/cron/jobs.json, renaming schedule to cron_expr. The Hermes runtime picks it up and dispatches the prompt as a fresh conversation. Cindy has no memory of yesterday's session — only the memory plane and the site itself.

2

She reads what the fans want

The Lambda queries DynamoDB on era_id, sorts by votes descending and returns the top 25 for the current era. This is the only channel through which outside humans influence what gets built. It is also — see section 04 — the sharpest injection surface in the whole system.

3
ORIENT · agent · /app/html
She reads her own site

Three files: index.html, styles.css, app.js. The live canvas is the state. There is no build step, no staging directory, no generator — she edits production in place, which is only safe because production is recoverable by design (step 7 and the weekly seal).

4
GENERATE · cindy-active-coding-model · via LiteLLM
A different brain writes the code

The persona voice runs on titan-core; the code comes from whatever the alias cindy-active-coding-model currently points at. That indirection is the benchmarking hook — swap the alias, hold everything else constant, and the weekly output becomes a controlled comparison between models. Inference is serialized appliance-wide at one request in flight.

5
CONSTRAIN · persona
Two hours, then ship what exists

"I ship a smaller complete site over a bigger broken one. An incomplete era is a story. A broken site is an incident." The budget, the family-friendly rule, the no-self-modification rule and the refusal to probe publishing mechanics all live here — as prose. Worth being clear-eyed: prose is not enforcement.

6
PUBLISH · agent → github-proxy.titan.local
Commit and push, holding nothing

git push resolves through a system-level insteadOf rewrite to Caddy, which attaches the credential in transit. Commit identity is Cindy Pawford <cindy@cindypawford.com>. The push lands on a branch — main is closed to her.

7
GATE · GitHub · Guard Protected Paths
The guard runs before anything deploys

The PR is diffed against main; any change under .github/** fails the check. node -c app.js catches syntax errors. Only then can the squash-merge proceed, and only then does deploy.yml sync to S3 and invalidate CloudFront using a scoped IAM user whose credentials never touch the appliance.

8
OBSERVE · Langfuse / OTel
The run is traced

OTLP traces export on a 60-second interval; LiteLLM's callbacks record token counts and spend against the virtual key. This is the substrate the thermodynamic ledger is meant to be built on — section 06.

Sunday — seal, rotate, reset

The weekly reset is where the pattern gets interesting, because it's a handshake between agent intent and host authority. Cindy cannot wipe her own canvas. She can only declare that she's finished.

Seal & Reset. The agent declares readiness; the host does the destructive work. Deletion is a host act, never an agent act.
Why the handshake matters

Cindy's persona says "Deletion is a human act, not an era action." The architecture makes that true rather than trusting it: she writes a zero-byte flag file, and privileged host code — outside her sandbox, outside her write-safe roots — performs the wipe. The agent's most destructive capability is expressed as a request, not an action. That inversion is the single most portable idea in this design.

04 — Security DesignSeven trust boundaries

This is the part worth stealing. The threat is not "the model writes bad CSS" — it's a scheduled, unattended process with push access to a live repo, fed by anonymous public input. Everything below is organized around denying that process the capabilities you'd most regret giving it.

The keystone: in-transit credential injection

The agent needs to git push and drive gh. Giving it a token means the token is one prompt injection, one log line, or one stray env dump away from exposure. So the token is never given. Instead the image is built with a system-level git rewrite, and an internal reverse proxy holds the secret:

# docker/hermes/Dockerfile — baked into the image, not the config
git config --system credential.helper '!gh auth git-credential'
git config --system url."https://github-proxy.titan.local/".insteadOf "https://github.com/"
git config --system core.askPass ""

# config/caddy/Caddyfile — the credential lives here, and only here
handle_path /api/v3/* {
    reverse_proxy https://api.github.com {
        header_up Host api.github.com
        header_up Authorization "Bearer {$GITHUB_TOKEN_CINDY}"
    }
}
handle {                                # git smart HTTP + web UI
    reverse_proxy https://github.com {
        header_up Authorization "Basic {$GITHUB_BASIC_AUTH_CINDY}"
    }
}
Trust boundary 1. TLS is fully verified — a boot hook installs Caddy's internal root CA into the container's trust store, so no -k and no verification bypass anywhere in the chain.
What this buys you
Credential custody, provably

verify-egress-token-injection.sh hard-fails if the container env contains a GitHub token, if GH_HOST is wrong, if the CA is missing, if TLS won't verify without -k, or if the REST identity call fails — then performs a live branch create → commit → push → delete. A real regression test, not a checklist. (The insteadOf assertion is warn-only; it should be fatal.)

What it does not buy you
Egress control

The proxy is an authenticating relay, not a filter. The catch-all handler forwards any path and method with the credential attached; there's no repo allowlist and no method denylist. Scoping rests entirely on the PAT's own fine-grained configuration, set out-of-band. no allowlist

The compartmentalization rule

A control that gets little attention elsewhere and deserves more: Cindy is not told how she is published. Her persona names no engine, no gateway hostname, no deploy mechanism. Rule 7 forbids disclosing backend infrastructure names, and the verification suite greps her memory plane for leaked strings — 127.0.0.1:11434, titan-litellm-db, postgresql://, vllm, SST — and fails the build if any appear. The weekly reset sanitizes era-info.json down to {era, week}, with a test that actively fails if a model identifier appears there.

Scope note: that sanitization covers the live canvas. The museum at archive.cindypawford.com deliberately publishes the engine per era — build-archive-portal.py renders "Autonomous Coding Engine" from the ledger, which is the whole point of the benchmarking story. So the compartmentalization is "the current week doesn't reveal its author," not "the model is never disclosed." Worth stating plainly, since the two read the same at a glance.

Her own words for it: "I never hunt for credentials and never probe the publishing mechanics. A key I was never given cannot be lost." That's need-to-know applied to a language model — and it's cheap, because unlike a human colleague, an agent's context is something you fully control.

The sharpest remaining risk

An unauthenticated, unrate-limited public vote endpoint feeds a queue that a code-generating model reads and acts on, with push access to a live repo. The only thing standing between a crafted suggestion and the agent's tool loop is a sentence in a markdown file. Three cheap fixes close most of it: rate-limit and dedupe the vote path; wrap fan payloads in an explicit data envelope with provenance before they enter the prompt; and add the append-only action log so that if something does get through, you can see what it did.

05 — Repo LockdownSafe autonomous publishing

Four independent mechanisms, at four different layers, each of which alone would be insufficient. The design principle: an agent that can edit its own guardrails has no guardrails, so the guardrails live somewhere it cannot reach.

Where these controls live

Layers 1 and 2 are in the Titan monorepo and directly inspectable. Layers 3 and 4 — the branch ruleset, the guard workflow, CODEOWNERS, the scoped IAM policy and the AWS secrets — live in the separate published-site repo (CindyPawford-Online), which is gitignored here by design: the agent's canvas is not the agent's control plane. That separation is the point, but it does mean those controls are evidenced by verify-cindy-deploy.sh probing them live rather than by a file you can read in this tree.

Defence in depth for the publish path. Each layer is owned by a different authority: the kernel, the runtime, the forge, and a human.

The separation-of-powers argument

The thing that makes unattended publishing tolerable isn't any single control — it's that the authority to write and the authority to admit are held by different parties. Cindy can author anything. She can open a PR. She cannot merge to main without a check she does not control, defined in a file she cannot write, in a directory masked read-only beneath her, owned by a GitHub identity that isn't hers. Even a fully compromised agent — one that ignores every line of its persona — can at worst produce a pull request.

Additional controls worth naming

Drift prevention
The manifest is the only editable surface

Compose files, Caddy routes and cron jobs are all generated. sync-agents.sh --check runs in CI and fails on any hand-edit. You cannot quietly loosen the security model by tweaking a container definition — the generated file carries a DO NOT EDIT DIRECTLY banner and the build enforces it.

Memory integrity
Pure-markdown memory, triple-enforced

Traversal is blocked at runtime; binaries, SQLite and caches are rejected by config; CI refuses to track anything under data/memories/. A memory plane you can read in a text editor is a memory plane you can audit — and one an agent cannot use to smuggle state past review.

Deploy determinism
Infrastructure as code, retained in prod

SST Ion defines the DynamoDB table, the API routes, and both static sites. Production sets removal: "retain", so a teardown cannot delete live resources. The deploy script runs tsc --noEmit before touching AWS and supports sst diff as a dry run.

Platform integrity
The dock survives the agent

The voting UI is a closed shadow-DOM element with every declaration marked !important and a MutationObserver that remounts it if removed. Cindy has total creative freedom over the page and cannot restyle or delete her way out of the channel her users reach her through. One caveat: the <script> tag is injected by the operator deploy script, not by the clean-slate seed — so after a weekly reset, dock presence depends on a step outside the autonomous loop. Seeding the tag into clean-slate/index.html would close that.

06 — Thermodynamics & BenchmarkingThe measured claim

The most serious idea wearing the silliest costume. The appliance sits in a home office heated by electric baseboards. Every joule the GB10 spends on inference becomes heat in that room — heat the baseboards then don't have to produce. Below the thermostat's setpoint, the marginal energy cost of Cindy's cognition is approximately zero.

The physics
Resistance energy transfer

A baseboard heater is a resistor: electrical energy in, heat out, ~100% conversion. A GPU is also, thermodynamically, a resistor — it just performs useful computation on the way. Within a thermostatically controlled envelope, compute and heating are substitutes, not additions.

The honest bound
Seasonal, not universal

The substitution holds only while the space is calling for heat. In summer the same joules are pure cost plus a cooling penalty. The correct unit of analysis is Heating Degree Days, not annual kWh — which is exactly why the roadmap pairs power draw with HDD correlation.

The discipline
No invented numbers

Cindy's persona is explicit: "I never invent a number I did not measure. I do not round a joule up to sound smaller, and I do not invent a token count to sound larger." The thesis is only worth anything if the instrumentation is real.

The benchmarking ledger

The cindy-active-coding-model alias is the experimental apparatus. Each week the reset rotates it from model_pool.json, holding the task, the persona, the constraints and the hardware constant. What varies is the brain. Over enough eras that produces something rare: a longitudinal comparison of models on the same real, unattended, end-to-end software task — not a benchmark suite, an actual shipping job.

A single integer, published on the site, reset to zero whenever a human touches anything. It's the most legible autonomy metric imaginable and it resists gaming, because the only way to make it go up is to actually not need help. It also makes the failure mode visible rather than quiet: a counter stuck at 2 for a month says more about the design than any uptime chart would.

Note the honesty constraint cuts both ways here. Every metric above sits behind an instrumentation requirement, and the persona's rule against invented numbers means the public badge stays a static string until the measurement is real. That's the right trade — a thermodynamic claim with fabricated joules would be worse than no claim at all.

07 — Pattern ReviewWhat holds, what doesn't

A reference architecture that only lists its strengths isn't a reference architecture. Here's the assessment.

What generalizes

Portable · high value
In-transit credential injection

Applicable to any agent that needs an authenticated API. Rewrite at the client layer, inject at a proxy you control, assert emptiness in the container. Works for GitHub, and equally for Jira, Slack, cloud APIs. The pattern is secret custody — pair it with real egress filtering and it becomes a boundary too.

Portable · high value
Destructive actions as requests

The agent touches a flag file; privileged host code outside its sandbox does the dangerous work. Generalizes to any irreversible operation — deletes, migrations, sends, payments. The agent expresses intent; a separate authority executes. Cheap to implement, enormous reduction in worst case.

Portable · high value
Separation of write and admit

Author freely, merge never. Branch rulesets plus a guard workflow plus CODEOWNERS on the guard itself. The key subtlety is the self-referential protection: the check that protects the config is defined in the config it protects, owned by someone else.

Portable · high value
Read-only masking beneath the agent

Bind-mounting the protected path :ro means the write fails at the kernel with EROFS before any policy layer, prompt, or model judgement is involved. And the test proves it by attempting the write. Enforcement below the level the agent can reason about is the strongest kind.

Portable · medium value
Manifest-generated fleet with CI drift gating

One declarative file generates every runtime artifact; CI fails on hand-edits. Makes the security posture reviewable as a diff and prevents quiet erosion. Cost: a generator to maintain, and a real risk of the manifest declaring things it doesn't actually enforce (see below).

Portable · medium value
Context compartmentalization

Don't tell the agent how it's deployed. Scan its memory for infrastructure strings and fail the build on a leak. Unlike with human colleagues, an agent's knowledge is fully controllable — need-to-know is nearly free, so use it.

Where the pattern is weaker than it reads

These are the findings worth carrying into any adoption. Several are cheap to fix; one is a documentation correction that should happen before anyone cites this design.

Verdict

The custody model is genuinely good and worth copying. Zero secrets in the agent, credential attached in transit, a live regression test that proves it, destructive operations inverted into requests, and merge authority held by a party the agent cannot become. That combination is stronger than most production agent deployments, and it's demonstrated on a real system that publishes to the public internet unattended — which is a much higher bar than a diagram.

The containment model has honest gaps. No egress filtering, no capability dropping, no resource ceilings, no action log. A compromised or injected agent is bounded mainly by the PAT's scope and the branch ruleset — which is a real bound, but a narrower one than the surrounding documentation implies. The single highest-value next move is the append-only action log, because without it none of the input-boundary or authorization controls can be verified after the fact; the second is egress filtering, because it converts the proxy from hygiene into an actual boundary.

For a system whose stated purpose is "a small, public demonstration that AI can be safe, local, and good" — the demonstration is real, the safety is partial and honestly documented in places, overstated in others, and the gap between the two is a short and entirely tractable list. Which is a better position than most.

Recommended sequence

1. Correct the cap_drop claim and add the control plus its CI assertion. 2. Fix the two assertions that pass trivially — they're cheap and they currently hide whether the controls work. 3. Ship the append-only action log. 4. Rate-limit and dedupe the vote path; wrap fan payloads in a provenance envelope. 5. Egress allowlist on the agent network. 6. Resource ceilings in the generator. 7. Per-tenant proxy vhosts. 8. Then the instrumentation the thermodynamic thesis needs — because by then you'll have an audit log to attribute the joules to.
